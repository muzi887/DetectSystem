结合你仓库里的 **README**、**`软件使用说明书.md`**、**`docs/`** 和部分 Vue 页面，查重和「AI 味」主要会打在**文字材料**上，代码本身反而次要。下面按「查什么 → 哪里高风险 → 怎么改」给思路（前提是内容真实反映你们自己做的系统，而不是靠洗稿应付检测）。

---

## 1. 先分清两类检测

| 类型 | 常见场景 | 主要看什么 | 对本项目的影响 |
|------|----------|------------|----------------|
| **文本查重** | 软著说明书、论文、竞赛材料 | 与库内文档、往届作品、网络文章的相似度 | **`软件使用说明书.md`、Word 导出稿** 风险最高 |
| **AIGC / AI 检测** | 部分高校、平台 | 句式均匀、套话密度、结构过于工整 | 说明书第一章、About 文案、部署说明里「赋能」「闭环」「异构」等堆砌处 |

软著/挑战杯往往**说明书 + 源程序**一起交：源程序查重看代码重复；说明书查重看叙述是否与公开模板、往届项目雷同。**两套都要处理，但手段不同。**

---

## 2. 本项目里容易被标红的特征（对照自查）

**文档侧（优先改）**

- **`软件使用说明书.md`**：大量竞赛/软著模板句式，例如「深度融合」「空天地一体化」「多源异构」「闭环决策」「最大限度减少」；章节结构是标准「背景 → 价值 → 分步操作 → 预期效果 → FAQ」，和网上软著范文高度同构。
- **操作说明过于「说明书体」**：每一步都写「点击 → 输入 → 预期效果」，且用语统一（如「异构数据流」在说明书与 `RelatedData.vue` 里一致），像一次性生成后贴进代码。
- **README / 部署段**：「全天候稳定」「隔离的虚拟环境」「防止依赖冲突」等偏宣传、少你们服务器上的真实细节（域名、路径、踩坑）。

**代码侧（次要，但影响「像不像学生/团队写的」）**

- 注释偏「教学模板」：如 `Home.vue` 里「直接使用布局组件，无需重复编写 Header」——像教程备注，不像团队内部注释。
- 界面文案与文档**一字不差**（如「正在接入异构数据流...」），查重会把 UI 字符串和 Word 说明书一起算进去。
- 若大量页面结构、命名、注释风格完全一致，代码查重也可能和开源 Vue  admin 模板或往届作品片段撞上。

## 3. 降查重思路（让文字「只可能来自你们项目」）

核心原则：**用「你们做过的事」替换「行业通稿」**，而不是同义词替换（降重工具常仍会被 AI 检测标出）。

1. **从真实开发过程反写说明书**  
   - 写：你们怎么定的 88 端口、PM2 进程名、`db.json` 里监测点字段含义、登录为什么用手机号、Flask 实际返回什么 JSON。  
   - 删/改：与实现无关的「卫星遥感」「深度学习算法」等大词（若代码里只是 mock/假接口，文档不要写满配架构）。

2. **结构打散，别用全网统一的软著目录**  
   - 可改为：先「系统能做什么（配截图）」→「环境怎么起（你们本机命令）」→「各模块与对应文件/接口」→「已知限制与 mock 说明」。  
   - 操作步骤保留，但**每步写你们界面上的真实按钮文案、路由路径**（`/warnings`、`pnpm mock`），少写「进入主界面 → 点击顶部导航栏右侧用户区域」这种泛化长句。

3. **增加不可伪造的细节（查重率会明显下降）**  
   - 竞赛/学校/队名、河北地质大学、具体测试账号、服务器 IP、mock 端口表、某次调试 bug（如 SPA 404 用 `try_files` 解决）。  
   - 配**你们自己截的图**（说明书里已有 `attachments/`，继续用实拍，别用 stock 描述）。

4. **源程序清单与代码一致**  
   - `scripts/add_code_to_docx.py` 导出的 Word 若与仓库不一致，人工比对会露馅；导出前统一改一轮，避免说明书写 A 模块、代码里叫 B。

5. **引用与借鉴要标注**  
   - Leaflet、Ant Design Vue、json-server 等若参考官方示例，在说明书「技术说明」里写清「基于某某示例改造」，避免整段与官方 README 重合。

## 4. 去 AI 味思路（让文风像人写的）

AI 文常见特征：**对称排比、抽象名词堆叠、每节长度相近、缺少口语和失误、没有个人判断**。

| 做法 | 示例方向 |
|------|----------|
| **删套话，改白话** | 「多源异构数据」→「监测点 JSON、预警列表和图表里的假数据」 |
| **写取舍和限制** | 「病害识别目前为 Flask 返回的模拟结果，未接真实模型」比「基于深度学习的智能识别」更真 |
| **句式长短不一** | 混用短句、列表、一两句吐槽（「json-server 改完会写回 db，别手改文件时被 dev 覆盖」） |
| **团队分工与个人口吻** | About 里成员介绍可写各自实际写的页面（谁做的 Map、谁写的 mock） |
| **代码注释像同事对话** | 去掉「注意：由于 AppLayout 已经…」；改成 `// 预警数：未 handled 的 alerts` |
| **统一术语表** | 全文固定叫「预警中心」或「灾害预警模块」，不要 AI/智慧/智能 轮换堆砌 |
| **人工二遍** | 一人按说明书操作一遍，把和界面不符的句子改掉——这类修改天然去模板感 |

**不建议**：纯同义词替换、乱序段落、无意义插入字符——查重可能略降，AI 检测和人工审核仍容易识别。

---

## 5. 代码层可做的（配合源程序查重）

1. **注释**：只保留业务非显而易见处（登录 token 存哪、proxy 规则）；删掉「步骤 1、步骤 2」式教程注释。  
2. **命名与结构**：在不大改功能前提下，组件内变量、CSS 类名、部分文案改成你们习惯的中文/英文混用（与文档一致）。  
3. **抽离重复**：多个页面相似的图表配置，可提到 `composables/` 或 `utils/`，减少大段重复块被代码查重标红。  
4. **第三方代码**：确认没有整文件粘贴未改的开源 demo；若有，保留 license 注释并改写逻辑。  
5. **导出 Word 前**：用 `eslint`/格式化统一风格即可，不必故意写乱；软著要的是**完整、可读、与运行一致**。

## 7. 合规提醒

- 查重/AIGC 工具是**辅助**；评委和软著审核更看**能否演示、代码是否与说明一致**。  
- 目标是**准确描述你们已实现的系统**，而不是「骗过检测」；与实现不符的「深度学习」「卫星遥感」反而在答辩时成为风险点。  
- 若学校对 AI 辅助写作有规定，应在材料中按学校要求声明使用范围。
