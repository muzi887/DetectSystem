## 未实现的测试点
如果你只是在系统里留了个入口（比如一个下拉菜单里的按钮），但实际代码没写、页面打不开，从标准的软件测试角度来看，**它不仅算一个测试点，而且是一个会直接导致测试失败（Fail）的缺陷（Bug）。**

在软件工程的标准中，黑盒测试是严格基于需求文档（即你的《软件使用说明书》）来构建用例的。说明书里写了用户菜单包含“个人中心”，测试流程就会包含“点击并验证个人中心页面加载”。如果在系统架构中，前端发起了对个人中心的路由请求，而系统没有提供对应的页面或后端接口，点击后无响应、报错 404 或页面白屏，这在测试报告中会被记录为功能缺失或严重异常。

针对这类在当前版本未实现的功能，为了保证项目的系统稳定性和最终的演示/检查效果，你需要进行相应的防御性处理。以下是三种技术处理方式：

### 1. 前端事件拦截与提示（推荐）

如果保留入口，必须阻止它发起无效的路由请求或接口调用。你可以在前端拦截该按钮的点击事件，阻止默认跳转，并调用全局组件弹出一个提示（Toast/Message），例如：`"当前版本暂未开放，敬请期待"` 或 `"系统升级中，功能暂不可用"`。

- **对测试点的影响**：测试点依然存在，但测试目标变为了“验证点击个人中心时，系统是否正确拦截并弹出提示”。
    

### 2. 移除或禁用前端入口

如果该功能对核心业务流（如灾害预警、数据监测）没有直接影响，最干净的做法是在 Vue/Ant Design 的前端组件中直接隐藏（`v-if="false"`）或置灰禁用（`disabled`）该入口。

- **对测试点的影响**：该功能不再作为测试点。你需要在测试范围中明确剔除该项，并且建议同步更新你的《软件使用说明书》，将未实现的功能从“系统功能概览”中删除，做到文档与代码一致。
    

### 3. 提供纯静态 Mock 页面

如果因为项目要求必须展示这个界面的存在感，你可以快速编写一个仅包含静态 UI 布局的 Vue 页面。使用写死的 Mock 数据填充头像、用户名等信息，不发起任何真实的后端网络请求。

- **对测试点的影响**：测试点保留，但预期结果变为“成功加载个人中心静态页面，静态信息展示无误，无控制台报错”。
    

**总结来说**：只要功能入口暴露在 UI 界面上，它就是合法的测试目标。如果功能确实没做，最严谨的做法是**隐藏入口并修改说明书**（剔除该测试点）；如果必须留着入口，就**加好前端拦截机制**，避免它演变成一个程序异常。
