# 假数据库迁真库方案（Mock `db.json` → MySQL 等）

> **实现路径已改（2026-08-22）**：不再用「Node 听 3000 + MySQL」。业务后端改为扩展 Flask，见 **[`Flask-MySQL替换Mock方案.md`](./Flask-MySQL替换Mock方案.md)**。  
> 下文的表拆分、API 兼容、规则链事务仍可对照；**编码与验收以新方案为准**。
>
> **云端库（2026-08-22）**：宝塔 MySQL 已建空库 `detect_system`，用户 `detect_system`。**业务只使用这一份**（本机 Flask 远程连接同一库，不另装 MySQL）。连接串与远程权限见新方案 §5.0。不要复用 `treescan_db` / `iot_db` 等其它项目库。
>
> **原目标**：把 `src/mock/db.json` + json-server 换成可并发、可备份的真数据库，**前端路径尽量不变**。  
> **现状**：业务 CRUD 与规则链落库都写同一份 JSON；Flask 识病记录另在 `analysis_records.json`，第一期 **不合并**。  
> **状态**：被 Flask 方案取代；本文保留作表设计参考。空库已有，表尚未建。

## 一、现在的假库有什么问题

| 现象 | 后果 |
|------|------|
| 整库一个文件 | 规则链 60 秒写回、人工改预警、多请求同时 PATCH，容易互相覆盖 |
| 进程内锁只管 Node 线程 | 与 Flask、以后多进程 Mock 各写各的 |
| 宝塔靠拷 `db.json` | 无法按表备份、无法权限分离、密码明文躺在仓库里 |
| json-server 查询语法 | `?_sort=time&_order=desc` 绑死前端，换库时必须在 API 层兼容 |

假库适合竞赛演示；要「多用户同时点、规则链一直跑、服务器可恢复」，就需要真库。

---

## 二、选哪种数据库

| 选项 | 适合本项目吗 | 说明 |
|------|----------------|------|
| **MySQL 8 / MariaDB**（推荐默认） | 是 | 宝塔默认就有；监测点、预警、用户都是关系表；运维文档现成 |
| **PostgreSQL** | 更合适「预报天数、虫情 factors」这种 JSON | `JSONB` 比 MySQL 的 JSON 好查；学校/宝塔要额外装，成本略高 |
| SQLite | 仅单机开发 | 文件库，并发写仍弱，不适合 60s 调度 + 网页同时写 |
| MongoDB | 不推荐当主库 | 现有数据是「表 + 外键」（pointId、fieldId），关系库更贴 |

**结论：**

- 线上与课程环境跟宝塔走 → **MySQL/MariaDB**。  
- 若从零搭服务器、且链 2/3 的数组字段会越查越复杂 → 可选 PostgreSQL，表结构与下文一一对应即可。  
- **不要让浏览器直连数据库。** 仍是 Vue → HTTP `:3000` → 服务端再访问 MySQL。

第一期保持 **Node 听 3000**（现有 `server.ts` 换掉 json-server 的写文件，改成 SQL）。不上 Django/Spring，不把识病 Flask 改成也连同一套用户表（除非第三期专门做统一账号）。

## 三、目标架构

```text
浏览器 / Vite 代理（路径不变：/monitorPoints /alerts /login …）
        ↓
Node :3000（现 mock/server.ts 演进为「真 API」）
        ├── 登录、规则链调度（60s）仍在这里
        └── mysql2（或 Knex）事务读写
                ↓
        MySQL：detect_system 库
                ├── users / monitor_points / alerts / …
                └── 规则链：rule_state、weather_readings、weather_forecast、…

Flask :5000
        └── 仍写 analysis_records.json（第一期不动）
```

`persistRules.ts` 里对「整个 db 对象」的修改，改成 **按表 UPDATE/INSERT**；`evaluateReading` 等纯函数 **不改**，它们不认识数据库。

## 四、表怎么从 JSON 拆出来

json 顶层每个键一张表。命名建议蛇形，API JSON 仍返回驼峰（在 Node 里转换），避免改 Vue。

| 现 `db.json` 键 | 建议表名 | 备注 |
|-----------------|----------|------|
| `users` | `users` | 第一期可仍存哈希前的密码，二期再 `password_hash` |
| `monitorPoints` | `monitor_points` | `id` 整型主键 |
| `weatherReadings` | `weather_readings` | `point_id` 外键；链 1 取每点 `id` 最大一行 |
| `alerts` | `alerts` | `time` 用 BIGINT 毫秒；`field_id` **字符串**（现网 `xiongxian`） |
| `fields` | `fields` | `id` VARCHAR，`monitor_point_id` |
| `ndviLayers` / `moistureLayers` | `ndvi_layers` / `moisture_layers` | |
| `thresholdProfiles` | `threshold_profiles` | `point_id` 唯一 |
| `ruleState` | `rule_state` | 联合唯一：`(point_id, rule_id)` |
| `weatherForecast` | `weather_forecast` | 一行一天，或 `days` 用 JSON 列 |
| `extremeEvents` | `extreme_events` | 去重键 `point_id + type + start_at` |
| `pestRiskPredictions` | `pest_risk_predictions` | `factors` 用 JSON 列 |

`alerts` 建议索引：`(handled, draft, point_id)`、`(time)`，对应列表筛选与 `_sort=time`。

规则链去重（未 `handled` 的 `pointId + ruleId + chain`）做成 **唯一索引** 或插入前 `SELECT`，替代 `dedupeAlerts` 的内存扫描。注意 `handled=1` 之后应允许再次插入同类规则。

## 五、API 兼容（前端尽量零改）

继续提供：

- `GET/POST/PATCH/DELETE /alerts`，列表支持 `sort=time&order=desc`（内部实现，不必再依赖 json-server 的 `_sort`）
- `GET /monitorPoints`、`GET /weatherReadings`
- `POST /login`（查 `users`）
- `POST /alerts/evaluate-all` 等规则链路由：内部改调 SQL 版 `runChain1OnDb`

json-server 会自动暴露所有集合。迁库后 **只保留前端实际用到的路径**（见 `src/stores`、`src/api`），不要把整库 REST 自动生成一遍以免漏权限。

环境变量：`DATABASE_URL` 有值走 MySQL；未配置时仍可读 `db.json`（开发机无库也能跑）。不要两种后端同时写同一份业务数据。

## 六、分步怎么落地（实现顺序）

### 步骤 0：库与迁移工具

- [x] 宝塔建库 `detect_system`、专用用户 `detect_system`（不要 root）。**空库已建**，详见 [`Flask-MySQL替换Mock方案.md`](./Flask-MySQL替换Mock方案.md) §5.0。  
- 表结构与导入改走 Flask / Alembic（不要再按下文写 Knex/Prisma 的 Node 路径）。  
- 密码只放宝塔与服务器 `DATABASE_URL`，不要写进仓库。

### 步骤 1：只换「写得最凶」的表

优先：`alerts`、`rule_state`、`weather_readings`、`threshold_profiles`。  
`runChain1OnDb` / 60 秒调度改为事务：读最新墒情 → `evaluateReading`（纯函数）→ 写 state + 插入 alerts。  
验收：页面预警中心与智慧决策与现在 JSON 版行为一致；并发点「处理」不会丢规则链刚写入的行。

### 步骤 2：预报与链 2 / 链 3

`weather_forecast`、`extreme_events`、`pest_risk_predictions`、`fields`、`ndvi_layers`。  
`runAllChains` 整段放进一个事务或按链分事务（链 3 失败不应回滚已成功的链 1，**按链提交**更稳）。

### 步骤 3：用户与监测点

`users`、`monitor_points`。登录改为查表。监测点状态若仍由前端推导，表里只存基础字段。

### 步骤 4（可选）：识病记录

`ml-bjj/serving/analysis_records.json` 迁到同一 MySQL 的 `analysis_records`，Flask 用 PyMySQL 或独立小服务写入。与业务库同实例不同库也可以（`detect_system` vs `detect_ai`），便于权限。此步 **不是** 把 3000 和 5000 合成一个进程。

### 步骤 5：下线 json-server 写文件

删除对整文件 `writeDb` 的依赖；`sync:mock-db` 改为「从 MySQL 导出种子」或只保留开发 SQLite 备选。部署文档改为：备份用 `mysqldump`，不再 scp `db.json` 当主数据。

## 七、规则链与并发

| 现逻辑 | 迁库后 |
|--------|--------|
| 读整个 JSON 到内存再写回 | 按 `point_id` 读读数与 `rule_state` 行 |
| `dedupeAlerts` 扫数组 | `INSERT` 前查未处理重复，或条件唯一索引 |
| `tickSensorSimulation` 改雄县那一行 | `UPDATE weather_readings SET soil_vwc=? WHERE id=?` |
| 文件锁帮不上多进程 | InnoDB 行锁；调度仍建议 **单 Node 进程** 跑 60s（多 worker 会重复跑链） |

`evaluateReading` / `detectHits` **保持纯函数**，单测继续用假时间、假数组。

## 九、验收

- [ ] 无 `db.json` 时，登录、监测点、预警 CRUD 可用  
- [ ] `POST /alerts/evaluate-all` 与 60s 调度写入 MySQL，刷新页面数据还在  
- [ ] 未处理的同一 `pointId+ruleId+chain` 不重复插入  
- [ ] 前端 `http.ts` 的 baseURL 与路径无需为迁库而大改  
- [ ] 宝塔可 `mysqldump` 恢复出预警与监测点  
- [ ] `DATABASE_URL` 为空时 Flask 明确报错（不回退 `db.json`）；本机与云上 Flask 都指向云端这一份 `detect_system`
