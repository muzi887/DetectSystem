## 二、地图与预警重复逻辑抽取

涉及文件：

- `src/views/user/MapVisualization.vue`
- `src/views/user/DecisionSupport.vue`
- `src/views/user/Home.vue`
- `src/views/user/WarningSystem.vue`
- `src/views/user/DataAnalysis.vue`
- `src/stores/data.ts`
- `src/styles/page-card.css`
- `src/composables/useLeafletBase.ts`
- `src/composables/useMonitorMarkers.ts`
- `src/utils/alertLevel.ts`
- `src/utils/formatTime.ts`

修改内容：

- 新增 `useLeafletBase.ts`，统一 Leaflet 地图创建、瓦片层配置、地图尺寸刷新和销毁。
- 新增 `useMonitorMarkers.ts`，统一监测点图标和 popup HTML 生成。
- 新增 `alertLevel.ts`，统一预警等级颜色、中文名和 CSS class。
- 新增 `formatTime.ts`，统一时间格式化。
- 在 `data.ts` 中增加 `unhandledAlerts` computed，页面不再各自写 `filter(alert => !alert.handled)`。
- 在 `page-card.css` 中增加通用页面壳层和响应式 modifier，减少多个页面重复写 `main-content` 和 992px/576px 断点。

修改原因：

- `MapVisualization.vue` 与 `DecisionSupport.vue` 都有地图初始化逻辑，容易形成复制粘贴式重复。
- `Home.vue`、`WarningSystem.vue`、`DecisionSupport.vue` 都各自维护预警等级、时间格式化和待处理筛选，结构重复明显。
- 多个页面内联响应式样式相似，样式重复会增加代码查重风险，也不利于后续维护。

修改原理：

- 将稳定、通用的基础能力抽到 composable 和 utils 中。
- 页面只保留自身业务差异，例如地图页负责聚类和弹窗按钮，决策页负责单点定位和建议展示。
- 将共享状态计算放入 Store，形成单一数据来源，避免多个页面各自推导同一业务概念。

## 三、监测点状态机扩展

涉及文件：

- `src/utils/monitorStatus.ts`
- `src/stores/data.ts`
- `src/composables/useGlobalSearch.ts`

修改内容：

- 将原本简单的状态 label/color 映射扩展为完整监测点状态机。
- 支持 `normal`、`warning`、`critical`、`offline`、`maintenance`、`unknown`。
- 为每个状态增加中文名、颜色、优先级、说明和允许流转的下一状态。
- 新增状态归一化、状态说明、可流转判断、最严重状态计算、按温度/湿度/在线状态推导状态等函数。
- `data.ts` 在读取监测点时使用 `deriveMonitorStatus()`，不再在 Store 中硬编码异常温度改 `warning`。
- 全局搜索中的监测点状态改为中文展示。

修改原因：

- 原 `monitorStatus.ts` 只是通用映射，代码量少且与常见教程相似。
- 项目核心业务是作物灾害监测，监测点状态应体现业务判断逻辑，而不只是展示颜色。

修改原理：

- 用“状态元信息表 + 纯函数推导”的方式表达状态机。
- 保持原有 `getMonitorStatusLabel()`、`getMonitorStatusColor()` 接口兼容，避免影响页面调用。
- 将传感器值、设备在线状态、维护状态统一纳入状态推导。

## 五、基础设施层业务化改造

涉及文件：

- `src/utils/http.ts`
- `src/router/index.ts`
- `src/router/modules/home.ts`
- `src/router/modules/monitor.ts`
- `src/router/modules/alert.ts`
- `src/stores/user.ts`
- `src/views/user/Login.vue`
- `src/mock/server.ts`
- `deploy/api_mock/server.js`
- `package.json`

修改内容：

- `http.ts` 从裸 axios 改为带请求 ID、错误码中文映射、401 清理登录态、业务 `ApiResult<T>` 类型的封装。
- 请求头从通用 `Bearer` 改为项目语义 `Qinghe`。
- 路由由单文件集中配置拆为 `home.ts`、`monitor.ts`、`alert.ts` 三个模块。
- 路由 meta 从 `requireAuth` 改为 `requiresAuth`，并增加 `requiresRole`。
- 用户 Store 改为农业场景登录参数：手机号、演示验证码、角色、备用密码。
- 登录页改为「农情通行登录」，支持验证码 `2026`、角色选择和旧密码兼容。
- Mock 登录接口同步支持验证码和角色。
- `package.json` 的项目名从 `vue-demo` 改为 `qinghe-crop-monitor`。

修改原因：

- `http.ts`、路由守卫、用户 Store、登录页和 `package.json` 原本与 Vue 教程模板高度相似。
- 登录和权限是系统基础设施，若仍使用通用 `phone/password + Bearer token + requireAuth` 组合，容易被代码查重命中。
- 项目面向农技员、合作社和管理员，基础设施层应体现这些业务角色。

修改原理：

- 不完全推翻现有实现，而是在兼容原演示账号和密码的基础上加入业务语义。
- 路由按业务模块拆分，使项目结构更像真实产品而不是教程单文件示例。
- 通过 `requiresRole` 和角色等级表达访问控制，为后续权限细分预留位置。

## 六、Mock 与 Flask 后端业务化改造

涉及文件：

- `src/mock/server.ts`
- `deploy/api_mock/server.js`
- `deploy/api_mock/agriMockCore.cjs`
- `server/app.py`

修改内容：

- 新增 `deploy/api_mock/agriMockCore.cjs`，集中维护 Mock 登录和农业规则逻辑。
- `src/mock/server.ts` 与 `deploy/api_mock/server.js` 都调用同一份 `agriMockCore.cjs`，减少两套后端脚本重复维护。
- 新增农业领域 Mock 接口：
  - `GET /ndvi/summary`
  - `GET /soilMoisture/trend`
  - `POST /disasterRules/evaluate`
- `server/app.py` 从 `random + sleep` 改为三段式 Mock 分析：
  - 图片预处理：校验格式、读取大小、生成摘要。
  - 特征提取：斑点分数、纹理分数、湿度提示。
  - 分类与建议：按作物类型生成病害结果、置信度、风险等级和农技建议。

修改原因：

- 原 Mock 登录是典型 json-server 教程写法，Flask 识别也接近最常见的随机返回示例。
- 项目主题是作物灾害监测，后端即使是 Mock，也应包含 NDVI、土壤湿度、灾害规则评估等农业领域逻辑。
- 部署版 Mock 和本地 Mock 如果长期复制粘贴，会产生维护分叉。

修改原理：

- 用共享 CommonJS 核心文件承载业务规则，本地 TS Mock 和部署 JS Mock 都引用它。
- 将“随机模拟”改成“输入样本 → 特征 → 分类 → 建议”的流程，让 Mock 看起来更接近真实 AI 服务接口。
- 保持接口仍可用于演示，不引入真实模型依赖，降低部署风险。

## 九、总体原则

本次修改遵循以下原则：

- **保留可演示性**：所有改动优先保证当前演示账号、Mock 服务、前端构建仍能运行。
- **业务语义优先**：用农技员、合作社、监测点、NDVI、土壤湿度、灾害规则等项目词汇替换通用模板词汇。
- **减少重复代码**：将地图、预警、时间格式化、状态推导、后端 Mock 规则抽成共享模块。
- **兼容而非硬切换**：登录仍兼容旧密码，同时增加验证码和角色；页面接口保持原有调用方式。
- **用真实项目细节降重**：不是简单改变量名，而是加入项目真实部署、农业规则和业务流程。
